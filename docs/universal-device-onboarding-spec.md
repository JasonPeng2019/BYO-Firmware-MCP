# Universal Device Onboarding Specification

Status: implementation target

## Goal

Given an exact MCU ordering code and a local official datasheet, setup must let the agent resolve
locally available or official CMSIS-Pack/pyOCD support without asking the user for pack names,
target identifiers, addresses, masks, or partitions. The server must independently validate every
agent proposal before it becomes profile, memory-map, gate, or flash authority.

"Any MCU" means any MCU for which pyOCD can non-destructively attach through an available probe and
whose device description exposes enough machine-readable facts for the requested capability. A
missing fact disables only the capability that needs it. The server must never invent board wiring,
deployment ownership, security state, or destructive recovery policy from an MCU name or datasheet.

## Required behavior

### Inputs and agent research

1. The user supplies only a logical board name, exact package/order code, local datasheet path,
   intended physical probe, and ordinary project facts such as whether UART is used and whether
   existing firmware must be preserved.
2. The server validates, bounds, hashes, and captures the supplied PDF bytes. The agent may read it
   to find official support, but its numeric claims are hints and never become authority. Device
   geometry used by the server comes from the independently parsed exact CMSIS-Pack leaf; a
   disagreement or missing machine-readable fact disables the dependent capability.
3. The server first inspects verified local pack bindings and the pyOCD built-in target inventory.
   A built-in target name is only a research lead unless independent machine-readable metadata maps
   the exact part and geometry. If no unique exact pack-backed candidate exists, the server returns
   a bounded run-scoped research request for official support.
4. The agent returns an official pack source record. It never supplies
   memory ranges, erase geometry, identity registers, reset clocks, or deployment partitions.
5. A downloaded/local pack is opened only after raw-size/archive limits and digest checks. The
   server proves that the exact requested part exists in the PDSC, derives the canonical target
   from that leaf, passes the expected digest into the adapter, loads those exact bytes only, and
   performs a non-destructive live attach before promotion. Bytes changed between validation,
   attach, and promotion are refused rather than cached or promoted.

### Device, board, and deployment authority

Device facts, board facts, and deployment ownership are separate:

- Device authority: exact part aliases, target/core, physical flash/RAM, algorithms, SVD, and safe
  identity evidence from the verified support package, bound to the captured official datasheet.
- Board facts: selected probe, actual successful attach policy, UART use/attachment, and explicit
  user statements about external hardware. Reference-board wiring or transport policy is never
  inherited from an MCU match.
- Deployment authority: application/bootloader ownership generated by the server. Physical flash,
  an ELF layout, or blank image sectors are not ownership.

### Capability ladder

1. `candidate_resolved`: inventory and planning.
2. `connected`: bounded diagnostics only.
3. `identity_verified`: gated read/debug; exact and compatibility proofs remain distinguishable.
4. `physical_map_verified`: artifact containment can be evaluated.
5. `deployment_verified`: guarded flash is allowed only within a server-generated allocation or a
   separately reviewed board policy.

For a new generic board, the initial schema-v3 `memory_map.yaml` contains verified physical regions,
any machine-verifiable prohibited regions, nullable partitions, and deployment policy `none`. An
unknown peripheral/security range remains UNKNOWN and therefore denied; it is not guessed into an
allowlist. This is a successful bounded read/debug setup,
not a reason to borrow full-flash authority. Destructive recovery remains unavailable without a
separate reviewed recovery policy.

### Application ownership

ADR-0004 replaces the blank-only first-flash rule. A generic application allocation is created by an
explicit guarded flash plan after the server excludes non-programmable regions, verifies bounded
sector programming, validates the artifact, and binds its digest. The server derives a minimal
sector envelope; callers cannot supply ranges. Existing bytes inside that envelope may be replaced
under the approved plan, while unrelated sectors remain untouched. Later approved artifacts may
expand the allocation monotonically. The server atomically persists the allocation immediately
before programming, and a failed program retains it for a contained retry.

### Persistence and currentness

- `memory_map.yaml` remains the only persisted safety authority.
- Profiles persist the canonical resolved-support record, not agent prose or permission state. The
  promoted project index and exact bytes live together below `.firm/packs`; the checkout registry
  is never a runtime setup write target.
- Every load/refresh replays exact pack bytes, PDSC leaf, target binding, datasheet digest, parser
  version, and profile semantics. Changed evidence refuses currentness.
- Plans, permissions, candidate IDs, mismatch allowances, and live identity stamps are run-scoped.
- Existing schema-v2 catalog profiles remain readable compatibility records; no new generic board
  receives reference-board partitions or transport policy through that path.

## Failure behavior

Unsupported or ambiguous targets return bounded research/remediation, not a raw exception. Missing
identity evidence permits connection diagnostics but not a live gate. Missing erase or deployment
facts permits read/debug but not flash. Locked targets never trigger unlock or mass erase
automatically. No caller-supplied range can establish safety authority.

## Acceptance

- Synthetic packs for unrelated vendors/cores prove exact leaf discovery, promotion, restart replay,
  geometry derivation, ambiguity handling, and tamper refusal without board-specific code.
- Fresh-root MCP tests prove the research continuation creates generic support and a schema-v3 map.
- Boundary tests prove zero backend mutation for unsupported identity, missing deployment authority,
  changed pack/datasheet bytes, and out-of-range artifacts.
- Existing reviewed profiles remain compatible, while a custom board can never inherit their board
  or deployment policy merely because the MCU matches.

## Resolved authority assumptions

ADR-0003 supersedes the earlier admin-only provisioning rule. Runtime discovery is permitted only as
a quarantined setup transaction: an agent locates bytes, while the server derives and replays every
fact. A promoted project manifest is an index to exact bytes, not authority by itself.

The application transition extends schema v3 rather than adding a second file. Its closed deployment
policy is either `{kind: none}` or `artifact_application_allocation` with exact sector ranges,
bounded-driver proof digest, creation map/artifact digests, optional parent allocation digest, and a
domain-separated allocation digest. Creation/expansion is atomic and requires an approved guarded
flash plan. Refresh may reproduce but never create or widen it.

Identity proof flows from the resolved support record into the profile and validator. Gate stamps
record `exact` or `compatible`; absence of either never stamps. Under ADR-0004, either proof permits
ordinary guarded application programming when the exact pack/target/map, bounded driver, artifact,
and explicit plan permission all agree. Compatible identity alone still cannot authorize bootloader,
unlock, mass erase, provisioning, or destructive recovery operations.

Datasheet evidence is a closed record of capture-parser version, canonical project reference, and
PDF digest. It establishes immutable correspondence to the user/agent research source, not numeric
memory authority. Changed capture parser or PDF bytes make the current map stale and require
refresh; failed refresh leaves the prior map untouched. A future semantic extractor may add typed
page/span facts only through a new parser/schema version; setup must not pretend arbitrary PDF text
has been independently interpreted today.

Pack promotion is a serialized read/merge/write transaction. It rebinds the final pack file to the
same bounded payload used for validation and live attach before publishing the manifest entry, so
concurrent boards cannot lose each other's bindings and changed quarantine bytes cannot be promoted.
