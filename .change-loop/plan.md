# Change implementation plan

## Source change list

- Source: `.change-loop/changes.md`
- Goal summary: Verify and correct only the four reported MCP correctness defects: reset-connect must be driven solely by its validated action plan, multi-image native builds must expose rather than reject candidates, flash completion must report only an observed reset state, and destructive recovery must invalidate its debug session.

## Plan items

### CL-001 — Make connect-under-reset independent of ambient launch overrides

- **What to change:** Confirm the current ambient reads (`PYOCD_BOARD_CONFIG`, `PYOCD_PROBE_UID`, and target fallback) and make the `connect_under_reset` path resolve its board, probe UID, and target only from the board/profile and its action parameters. Thread that explicit result to the backend without allowing the pyOCD adapter’s `connect_under_reset` implementation to reintroduce environment fallbacks when an explicit value is absent. Update the reset-connect tool/plan guidance to say that launch-environment overrides are ignored and to direct callers to the action’s explicit `probe_uid`/`target_override` inputs or persisted board setup.
- **Where:** `src/pyocd_debug_mcp/server.py` (`resolve_board_config`, `_resolve_probe_uid_for_connect`, `_connect_under_reset_impl`); `src/pyocd_debug_mcp/adapters/swd_pyocd.py` (`PyOCDSWDInterface.connect_under_reset`); `src/pyocd_debug_mcp/guardrails/plan_defs.py` (connect-under-reset guidance); `.env.example` and any reset-connect wording in `README.md`; focused tests in `tests/test_swd_pyocd_jlink_multisession.py` and the existing server connection test module.
- **Exact intended behavior:** With `PYOCD_BOARD_CONFIG`, `PYOCD_PROBE_UID`, and/or `PYOCD_TARGET` set to conflicting values, a `connect_under_reset` request uses only its verified board profile plus supplied action parameters; it either attaches through that resolved route or fails honestly. An omitted probe UID follows the existing profile-based probe-resolution/auto-detection behavior, never an ambient UID. An omitted target follows the selected board/profile or pyOCD auto-detection, never an ambient target. The successful response/event continues to say `target_state: halted` only after the existing observed halt check.
- **Must remain intact:** The normal `open`/`connect` and expressly guarded manual override paths retain their documented launch-environment compatibility. Explicit `probe_uid` and `target_override`, profile pack/PDSC pinning, reset-line availability refusal, cleanup on failed attach, and the existing “halted and reset line released” postcondition remain unchanged.
- **Objective verification:** Mock pyOCD session selection with conflicting environment values and assert reset-connect passes the profile/action-selected board, UID, and target to the backend; repeat with omitted optional parameters and assert no environment value is passed or selected. Assert the normal non-reset open path still accepts its documented ambient fallback. Assert no board is assigned after a failed reset attach and the fake session is closed. All assertions run with fake sessions only.

### CL-002 — Return ambiguous native-build artifacts as candidates instead of rejecting valid multi-image outputs

<!-- Assumption: Preserve the existing explicit `--artifact[-elf|-map|-hex]` selection interface rather than adding a new selector; automatic discovery is allowed to report candidates but must not select an image when more than one eligible ELF or MAP exists. -->

- **What to change:** Replace singleton-only automatic ELF/MAP discovery with deterministic candidate collection. When exactly one eligible ELF and one eligible map are discoverable, preserve the current selected-artifact result. When either role has multiple eligible files, do not fail the otherwise successful build merely for multiplicity; return machine-readable absolute candidate paths for every ambiguous role, leave that role unselected, mark the artifact selection as requiring an explicit existing declaration, and provide the existing `--artifact-elf`, `--artifact-map`, and/or named `--artifact ROLE=PATH` remedy. Continue validating explicit declarations exactly as today.
- **Where:** `src/pyocd_debug_mcp/native_build.py` (`_artifact_paths`, build evidence schema, `_artifact_assurance`, `run_build`, parser help, and `command_template` guidance); `README.md` native-build documentation; tests covering `native_build` discovery and CLI/build evidence (add a focused `unittest` module if no existing native-build test owns this behavior).
- **Exact intended behavior:** A successful build tree containing several structurally loadable ELFs and/or nonempty `.map` files returns exit code 0 with its process evidence plus sorted candidate lists and an unambiguous status/remedy; it does not claim an `elf`, `map`, or matching HEX selection and downstream flash planning cannot treat any candidate as selected. A caller then reruns the same build with explicit artifact paths and receives the current validated selected artifact fields. Zero eligible ELF or map candidates remains an honest missing-output/selection-required failure, and multiple same-stem HEX files for a selected ELF remain an explicit-HEX selection requirement rather than a guessed choice.
- **Must remain intact:** The helper still executes only the supplied native argv, does not choose a build system/toolchain/image, constrains discovered/declared paths to the captured build root, validates explicit ELF/HEX formats, retains known artifact/evidence field compatibility for unambiguous builds, and never presents a candidate as flash authorization or map/ELF coherence proof.
- **Objective verification:** In temporary build roots populated with minimal valid ELF fixtures and map files, assert: one ELF/map retains the legacy selected fields; two ELFs and/or maps yields exit 0, no selected value for each ambiguous role, every resolved candidate path in deterministic order, and an explicit-declaration remedy; zero candidates produces the documented failure evidence; and explicit `--artifact-elf`/`--artifact-map` selects and validates one named candidate. Assert a multi-image result is not fed as a selected flash artifact. Tests use a mocked successful process and files only.

### CL-003 — Report post-program reset state only when it is observed

<!-- Assumption: A successful program/verify followed by an unobservable final reset is useful but incomplete work, so it should be returned as a successful programming result with `reset_state_unconfirmed` rather than fabricated as running or reclassified as a write failure; a failed pre-program reset/program/verify remains a failure. -->

- **What to change:** Give the programming backend a truthful post-reset outcome instead of swallowing final-reset `TransferError` and returning `None`. After successful program/verify, distinguish observed `running`, observed `halted` (when requested), and `reset_state_unconfirmed` when the final reset fails or its state cannot be read. Have `target_control.flash_firmware` and `FlashToolServices` propagate that outcome; render it in the flash tool response/event and update flash tool docs. Do not assert `running` unless a post-reset state read observed it.
- **Where:** `src/pyocd_debug_mcp/adapters/swd_pyocd.py` (flash/reset execution and state observation); `src/pyocd_debug_mcp/adapters/swd_interface.py` and `src/pyocd_debug_mcp/adapters/swd_process.py`/`provider_worker_runtime.py` if their flash return contract must carry the new result across the worker boundary; `src/pyocd_debug_mcp/services/target_control.py`; `src/pyocd_debug_mcp/server.py` flash-service composition; `src/pyocd_debug_mcp/tools/flash.py`; corresponding tool descriptions/guidance and focused adapter/flash-handler tests.
- **Exact intended behavior:** On successful program/verify plus observed final run state, `flash_application`/`flash_bootloader` report and log `target_state: running`; on the halted variant, they report `halted`; after a final-reset transport failure or failed state observation following successful programming, they report `target_state: reset_state_unconfirmed` with an actionable reconnect/state-check remedy and never use “target left running.” A programming/verification failure still raises/logs failure and does not emit a success outcome. No path fabricates a target state.
- **Must remain intact:** Flash containment/validation, sector erase behavior, programming verification, symbol/allocation lifecycle, event timing/error logging, and existing successful observed-running response compatibility remain intact. The pyOCD-specific final-reset tolerance is retained only as tolerance for uncertainty, not as proof of execution.
- **Objective verification:** With fake target/programmer objects, assert successful programming plus observed `RUNNING` produces the existing success wording/event; observed `HALTED` reports halted; and a final-reset `TransferError` or post-reset state-read exception produces a non-throwing successful-programming result labeled `reset_state_unconfirmed`, never `running`. Assert a programmer exception still propagates and logs `FAILED`, and process-isolated adapter result validation round-trips each allowed state without hardware.

### CL-004 — Close and invalidate the active connection after destructive recovery

- **What to change:** Replace the recovery-completed marker-only callback with a recovery-finalization operation that, after the typed recovery call succeeds, atomically removes the board’s active connection assignment, invalidates/revokes its dependent gates/plans/setup/unlock state, closes the backend session and runtime record, and records the recovery completion. Preserve/report cleanup failure honestly while ensuring no stale handle remains usable. Update `target_unlock` response/tool guidance to state that recovery disconnects the board and requires a fresh `connect` followed by validation before subsequent debug or validation actions.
- **Where:** `src/pyocd_debug_mcp/tools/unlock.py` (`UnlockToolServices`, `UnlockCoordinator.execute`, execution response); `src/pyocd_debug_mcp/server.py` (connection-manager/session cleanup integration replacing `_mark_unlock_completed`); `src/pyocd_debug_mcp/services/session_runtime.py` only if lifecycle record support is required; `src/pyocd_debug_mcp/guardrails/plan_defs.py` target-unlock guidance; tests for unlock coordinator and server disconnect/session ownership.
- **Exact intended behavior:** Once the backend recovery succeeds, the old `TargetSessionHandle` is closed and no longer returned by `handle_for`; later flash, memory, register, serial, validation, or debug operations on that board fail through the existing not-connected/validation-gate path until the caller makes a new connection and completes the required validation. The unlock result explicitly reports recovery completion plus reconnection/revalidation required. If recovery itself fails, preserve the current failure report and do not claim completion; if post-recovery cleanup fails, surface that uncertainty and still prevent reuse of the stale assignment.
- **Must remain intact:** Typed, plan-bound one-time recovery authorization; complete erase disclosure; report creation; gate clearing before destructive action; no physical hardware action in tests; and normal explicit `disconnect` cleanup semantics remain intact. Recovery does not silently reconnect or auto-select a different probe.
- **Objective verification:** Use fake connection manager, target-control close, session store, and recovery service to assert successful recovery calls backend recovery once, clears the exact current assignment, closes both backend/runtime resources, invalidates dependent state, marks/records recovery, and makes subsequent `handle_for` fail until a fresh assignment is made. Assert recovery failure leaves the completion path unreported, and a close failure is surfaced while the connection remains unavailable. Assert the returned JSON/text contains the reconnect-and-validate requirement.

## Out of scope / must not change

- Do not change ordinary `connect` environment-override compatibility, except where a shared helper needs an explicit flag to keep `connect_under_reset` isolated.
- Do not guess or auto-select a Zephyr/NCS image, introduce hardware/vendor branches, add environment-specific constants, or make physical hardware calls.
- Do not change artifact collection bundles, flash safety authority, target recovery mechanisms/permissions, build-system selection, or unrelated session behavior.
- Existing contracts not named for change remain unchanged.
- No unrelated refactors, dependency upgrades, formatting sweeps, commits, or generated artifacts.
