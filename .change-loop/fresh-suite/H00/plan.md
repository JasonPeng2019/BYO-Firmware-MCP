# Change implementation plan

## Source change list

- Source: `.change-loop/fresh-suite/H00/changes.md`
- Goal summary: Preserve the accepted H00 repository-verifier repair and make its owned-process implementation type-safe and truthful on both native Windows and native POSIX, so the complete locked verifier contract is green on each actual host.

## Repository context and assumptions

- Verified architecture and relevant entry points: `src/pyocd_debug_mcp/kernel/processes.py` owns owned-subprocess creation, Windows Job Object assignment/resume/cleanup, POSIX session creation, and process-group cleanup. `popen_owned()` applies `process_group_options()` before `subprocess.Popen`, then on Windows creates and resumes a kill-on-close Job; `run_owned()`, `kernel/operations.py`, and `adapters/swd_process.py` consume `terminate_process_group()`. `tests/test_process_cleanup.py` already asserts the Windows two-phase cleanup deadline, unconfirmed-cleanup result, suspended-leader handling, primary-error identity, and marker retention. The previously accepted H00 repository contract is in `tests/test_h00_repository_contract.py`; its Pyright negative control and candidate-clone gate already exercise the no-argument default command. `tests/test_h00_repository_regressions.py` owns the separate Pyright-scope regression.
- Existing test/build commands relevant to the change: `uv sync --locked`; `uv lock --check`; `uv build`; `uv run --locked --no-sync ruff check .`; `uv run --locked --no-sync pyright`; `uv run --locked --no-sync pytest --collect-only -q`; and `uv run --locked --no-sync pytest -q`. Actual Debian WSL2 evidence shows all but default Pyright/full pytest pass after the first repair: Pyright reports seven POSIX attribute-access errors in `kernel/processes.py`, and full pytest has three failures, including the Windows-path unit exercise on POSIX.
- Preservation boundary: retain byte-for-byte the reviewed `README.md`, `pyproject.toml`, and `uv.lock` recorded in `.change-loop/fresh-suite/H00/PRE_POSIX_REPAIR_MANIFEST.json`; use the recorded hashes of both existing H00 tests as the baseline for narrowly tester-owned portability/materialization diffs; do not edit `tests/test_process_cleanup.py`. Production ownership is exactly `src/pyocd_debug_mcp/kernel/processes.py`; no second production helper is authorized.
- Charter checkpoint protocol: every server-repair role rereads `../.codex/design_charter.md` before planning, before implementation, between distinct implementation features, and before each verdict, then states its check in its final role message; the firmware test agent remains charter-isolated. The planner has reread it before this plan: the plan keeps one small, runtime-resolved platform-access owner, preserves real cleanup evidence and failures, and adds no speculative portability layer.

## Plan items

### CL-004 — Make Windows-only API access portable and honest

<!-- Assumption: Keep the known Windows creation-flag bit values (`CREATE_NEW_PROCESS_GROUP = 0x00000200`, `CREATE_SUSPENDED = 0x00000004`) as local fallback values for the explicit `platform="nt"` option calculation when the executing interpreter omits those Windows-only names; this preserves the real Windows flags for intentional cross-host unit exercise without adding attributes to `subprocess` or pretending the Windows API exists. -->

- **What to change:** In `kernel/processes.py`, replace every direct platform-conditional read of `subprocess.CREATE_NEW_PROCESS_GROUP`, `ctypes.windll`, and `ctypes.get_last_error` with the smallest local runtime lookup(s) that centralize those Windows-only accesses. Use the lookup for Job creation, process resume, Job close, and Windows start-token inspection; make the creation-flag calculation return the real numeric Windows group-plus-suspended flags even when tested from a host where the symbolic `subprocess` names do not exist. When a Windows ctypes operation is actually invoked but its native loader/DLL/last-error accessor is unavailable, raise a contextual `OSError` chained from the missing-access failure rather than returning success, fabricating a DLL/API, or leaking a POSIX-only import/typecheck failure.
- **Where:** `src/pyocd_debug_mcp/kernel/processes.py`, specifically `process_group_options()`, `_create_windows_kill_job()`, `_resume_windows_process()`, `_close_windows_job()`, and `_windows_start_token()`; no new production module is needed.
- **Exact intended behavior:** Importing the module and the default no-argument Pyright run succeed on both actual Windows and actual POSIX with no Pyright suppression, `type: ignore`, broad `Any` conversion, platform-specific Pyright override, or reduction of `[tool.pyright].include`. `process_group_options()` continues to return `{"start_new_session": True}` on POSIX. `process_group_options(platform="nt")` returns `{"creationflags": 0x00000204}` whether or not Windows-only `subprocess` attribute names are present on the host. On Windows, `popen_owned()` still launches suspended with those flags, records the marker before Job assignment, assigns the real kill-on-close Job, and resumes the process. On POSIX, `popen_owned()` still uses `start_new_session=True`, and `terminate_process_group()` still signals and verifies the real process group. A call into a Windows ctypes operation on a host without its native APIs fails with an `OSError` describing unavailable Windows API access; it never reports successful Job creation, resume, close, or identity inspection.
- **Must remain intact:** Keep `validate_argv()`/`shell` rejection, marker schema and lifecycle, retry/grace constants, Windows two-phase Job active-zero then leader-reap cleanup budget, Windows job semantics, POSIX SIGTERM/SIGKILL/PGID-absence phases, failure propagation, original primary exception identity, marker retention on unconfirmed cleanup, and all public function signatures. Do not modify the reviewed H00 README/metadata/lock/test changes, unrelated production files, `tests/test_process_cleanup.py`, or any hardware/MCP behavior.
- **Objective verification:** Run `uv run --locked --no-sync pyright` with the existing source-only configuration and assert exit 0; run the existing `tests/test_process_cleanup.py` unchanged and assert its deadline, failure-identity, and marker assertions remain green. Regression coverage must delete or otherwise make unavailable the Windows-only `subprocess` names in a scoped test and assert `process_group_options(platform="nt")` is exactly `0x00000204`; invoke each native Windows-access entry through the new lookup with the loader/DLL/last-error capability unavailable and assert a contextual `OSError` plus no success side effect. A tester-owned automated diff guard compares the new `processes.py` additions against `HEAD`, the metadata/docs/lock hashes against `PRE_POSIX_REPAIR_MANIFEST.json`, and each existing H00 test diff against its narrow owner/scope; it fails on any added `type: ignore`, `# pyright` directive, `Any` import/annotation/cast, Pyright/config change, doer-authored test change, or tester-authored production change. On native Windows, exercise the unmocked suspended-Job path and assert the creation flags remain numerically correct and current cleanup behavior passes. On native POSIX, use an unmocked owned child to assert its PGID equals its PID/new session and, after `terminate_process_group()`, that the group no longer exists.
