# H04 REQ-008 — bind datasheet bytes to the accepted setup plan

Authorized local firmware-server validation. Scope is the local `BYO-Firmware-MCP` repository and
the already captured host-side H04 evidence. No remote or third-party target is in scope. The
repair itself is host-only and must not operate hardware.

## Verified defect

In two fresh isolated public-runtime observations, `board_setup-plan` accepted an exact
`datasheet_path`, the file changed after plan acceptance, and the server nevertheless allowed
`board_setup`/`board_fix_setup` to complete and persisted the changed digest as ready authority.

Main classification:

`../fresh-experiments/H04_20260725-100800/.agent-workspace/MAIN_SERVER_FAILURE_REVIEW_005.md`

## Required behavior

Reuse the server's existing generic plan artifact-digest binding so a populated
`board_setup-plan` binds the exact local PDF bytes at acceptance. Before either `board_setup` or
its paired `board_fix_setup` begins, a missing, unreadable, path-replaced, or byte-changed PDF must
invalidate and relock the plan and return the existing actionable artifact-change refusal. The
caller must submit a replacement plan for the current bytes.

An unchanged authoritative PDF must retain the current setup/repair behavior. Preserve:

- exact action parameter and permission contracts;
- paired setup/fix allowance semantics;
- the accepted H04 datasheet-applicability proof and durable provenance behavior;
- all board/vendor/OS generality;
- public plan guidance, now truthfully disclosing that datasheet bytes are bound;
- existing artifact-bound behavior for unrelated plans.

## Scope constraints

- Use no board, vendor, MCU, path, or OS special case.
- Add no arbitrary size/count/time limit or hostile-input hardening.
- Do not redesign setup, plan state, PDF parsing, pack resolution, or durable profile formats when
  the existing artifact-binding mechanism is sufficient.
- Do not edit firmware, fixtures, experiment evidence, or documentation outside the server repair
  artifacts and focused public-contract wording generated by the existing plan machinery.
- Do not commit, push, deploy, flash, erase, reset, or operate hardware.
- Read `.codex/design_charter.md` before planning, before implementation, between production
  changes and tests, and before declaring completion. Record each check in the selected
  change-loop runtime.

## Objective verification

Automated tests must prove at least:

1. plan acceptance records a `datasheet_path` artifact binding and advertises that binding;
2. changing PDF bytes after plan acceptance refuses before primary setup execution, invalidates
   and relocks both setup actions, consumes no hardware/setup workflow action, and directs a
   replacement plan;
3. changing bytes between the primary incomplete setup and paired fix also refuses before paired
   execution and leaves no completed/ready durable authority;
4. unchanged PDF bytes preserve successful primary/paired setup semantics;
5. wrong-family/correct-family datasheet applicability regressions and unrelated artifact-bound
   plans remain green.
